# 正文传输（AT02—AT09 · alpha31.13）

在“预设与 API”的通用、模式或任务路由中选择“抗截断传输”，默认关闭。当前支持 OpenAI Chat Completions（原生 OpenAI 或自定义 openai_compat）及自定义 Gemini generateContent；接口凭据仍归宿主管理。原 Vertex 执行路径和选项已移除，旧 vertex-streaming 值只为读取历史设置保留，下拉框不再生成旧选项，旧值按关闭显示并提示停用，不会自动改为开启新功能。

## 传输模式

“正文抗截断（含完整性检查）”已包含下述完整性检查，不需要另外开启。各模式互斥选择；正文抗截断内置完整性检查，不适用而旁路的请求不会进入对应处理。

- 正文抗截断：声明一个仅运输正文的临时函数，发送一次请求，还原其 content 参数。没有函数执行或结果回传。供应商必须支持工具选择和相应返回格式；忽略工具声明会报“未生效”，不自动降级。
- 仅检查完整结束：不添加工具或正文指令，验证实际响应完整性，便于诊断静默结束。它不改变模型输出策略，不是额外的抗截断技巧。

- 工具／搜索兼容检查：明确选择后，保留真实工具、搜索开关与工具历史，只检查完整响应，不添加正文工具或改变原请求。主聊天工具轮显示“工具调用响应完整，尚非最终正文”，交回宿主原有循环；最终正文轮另行判断。附属文字任务不执行真实工具。此模式不是工具正文包装，不会自动续写或修复断流。

流式开关继续使用原生设置。非流式保留非流式上游请求，不强制改成流式。OpenAI 工具参数可以逐块还原；自定义 Gemini 不强塞 Vertex 专属参数流开关，按实际返回的完整 args 或 partialArgs 解码，服务商可能整段交付正文，不能保证首字实时出现。

Responses、Gemini Interactions、其他 provider、代理、结构化输出、多候选与未知消息结构仍旁路。旧正文抗截断/仅检查模式还旁路真实工具/原生历史与搜索；兼容检查模式允许这些请求并保留原字段。AT09新增严格包装选项见下节。Unicode/图片转码未接入。不能删除工具历史来强开本功能。

## 完成与错误

只有完整的协议结束才放行成功状态及缇斯亚自动归档。流式缺结束原因、缺必要结束标记、坏 JSON/UTF-8、结束后继续送正文、长度上限、拦截、空回复、服务错误等会明确失败；取消、切聊天/连接、超时不补发。最近状态显示结束原因（如可得）、错误码、HTTP 状态、收到的字节和耗时。诊断字段不保存正文或密钥。

主聊天同时通过缇斯亚错误提示报告失败，不仅依赖宿主是否处理 SSE 错误事件。片段可以留在聊天显示，但不作为完整结果自动归档。若上游报告 STOP/stop，却语义上少写了一段，协议检查无法凭空识别。服务端 CPU 过载/503、网关504和模型输出长度上限也不会被此功能消除。

部分宿主把非流式 Gemini 响应转成 choices，并丢弃原始 finishReason；这类结果显示“宿主报告完成（原始结束原因不可得）”，不能当作原始 STOP 证据。可得的原生结束原因仍严格检查；工具参数的完整 JSON 和正文仍校验。

如果同时安装了社区抗截断扩展，请停用其中一个并重启，避免两次包装。更新后建议重启页面/应用，以卸载旧模块。接口不支持时保留错误，用户可明确切换模式；没有自动重试、自动续写或后台调用。

## 查看生效状态与分享上下文

打开缇斯亚配置→上下文一览，选择对应时间/任务。状态和下方JSON都属于选中的那次请求；“正文抗截断已生效”只在tool-text或tool-text-tools完成且正文还原成功时显示。“仅完整性检查已完成”不是工具正文抗截断；“本次未启用抗截断：请求已开启搜索”表示本次旁路。搜索开关开启不等于已经实际执行搜索。完整收到正文也不能单凭结果证明抗截断介入。

“复制当前记录”复制显示的JSON；自动剪贴板不可用或拒绝时明确报错并显示只读文本供长按复制。“导出当前记录”通过宿主file-export接口保存JSON，Android走宿主公共下载/系统文档选择流程；失败/取消不报成功、不修改配置、不触发模型调用。记录含原始正文和提示词，分享前可自行检查；此功能不是脱敏诊断摘要导出。

用户05:40报告重启后完整返回，截图该次最近状态为搜索旁路；不能据此断言抗截断有效或此前空回已修复。真实剪贴板/Android文件保存交互待设备验证。


## 工具与搜索的兼容边界

alpha31.6新增的是显式兼容检查，不宣称“正文工具包装+联网搜索”已经接通。它每个捕获请求只发一次，真实工具调用原有的模型→工具结果→模型往返仍可能多次。搜索开关只证明请求开启搜索，不证明后端保留或实际执行。

只读参考后端f6126b4f的makersuite构建器在存在function_declarations时省略google_search；用户安装APK的后端是否相同尚未执行验证。Google现行[generateContent组合工具文档](https://ai.google.dev/gemini-api/docs/generate-content/tool-combination)说明部分模型支持组合并需保留服务器工具上下文；任意自定义中转不自动具备相同能力。完整包装兼容需核具体接口与回合保存契约，未通过删除真实工具或覆盖搜索实现。

72项定向本地测试通过，详见tool-search-compatibility-validation.json。主聊天引用、签名和工具响应保留，工具轮不会触发最终正文自动归档。真实模型、后端和Android仍待验。


## AT07 · 媒体输入和图片输出

- “发送内联媒体”（media_inlining）与“请求返回图片”（request_images）是不同设置。前者负责输入，后者请求图片输出。原media提示合并了两种情形；现在按实际结构/输出开关分别记录。
- 三种有效模式支持宿主image_url、audio_url、video_url与标准input_audio输入。消息顺序、内容、画质、元数据保持；不下载、转码、删除媒体。原8 MiB请求/32 MiB响应上限保持，超限仍明确处理。
- verify-tools允许图片输出开关，保留OpenAI图片字段、Gemini inlineData及宿主非流式responseContent/native结构。文字加图片可正常完成；纯图片为media-complete，交宿主显示，不触发剧情正文自动归档；工具加图片仍为tool-handoff。附属文字任务不接纳纯图片。
- 普通tool-text/verify仍不接请求图片输出；不会静默换模式。音频/视频输出、fileData输出和未知结构不在本项验收范围。图片字节只作为不透明内容保留，协议完整不等于图片可解码或界面显示已验。
- 完整性内核新增默认关闭的内容识别回调，仅兼容检查传入已校验图片识别器；许可证保留，来源原hash和本地补丁hash分列。结束标记/长度/工具/错误检查保持。
- 用户截图同时勾选输入媒体与请求图片，支持request_images导致旧版旁路的解释；旧导出未记录此字段，不能追认为抓取到该次原始值。主动推进规则已进入其观察快照；不据历史回复宣称新模式行为验收通过。


## AT08 · 非流式宿主正文字段一致性

- alpha31.9用户报告verify-tools开启为空回、关闭可出全文。导出仅有406字节统计，无响应内容；不将本次具体根因定为上游空回或工具转换丢失。
- 子代理在独立31.9源码中调用实际fetch包装层及原样提取的宿主extractMessageFromData，以同一良性响应做13组OFF/ON对照。复现choice.text、顶层content的误拦，及顶层content=[]时误报完成。标准真实工具和动态合成工具恢复通过。
- 主聊天非流式检查现在依宿主nullish优先级选择正文：顶层content文本块 → message.content → choice.text → 顶层text。已存在的空字符串或空数组不回退。只投影检查用副本；verify-tools返回原完整响应。附属任务不借用主聊天独有的读取兼容。
- 不从reasoning、native或工具参数补正文，不虚构finish_reason；长度上限、过滤、缺结束信息仍拒绝。仅计数的responseShape和hostTextSource记录在检查前，辅助区分字段遗漏与响应确空；不保存响应文本/工具参数/URL。
- 467项本地测试及独立修后13组对照+1工具恢复通过。全量结果包含9项构建检查；无真实模型请求、Rust后端或Android验收。用户那次406字节响应的精确原因仍未知。


## AT09 · 正文工具包装（兼容工具回合）

新选项 `tool-text-tools` 是主动包装，包含完整性检查。它与 `verify-tools` 的检查模式不同，也不自动替换旧配置。

1. 保留原有标准函数工具和工具历史，追加一个随机命名、只携带 `content` 字符串的正文提交函数。无真实工具时强制选该函数；有真实工具时要求调用工具，允许先查资料，最后单独提交正文。宿主已有的指定函数选择保持不变；明确禁止工具或未知选择报冲突。
2. 真实工具回合只校验后交回宿主，保留ID、参数、原生签名及元数据；插件不执行工具、不伪造结果、不替宿主追加请求。模型若在同一回合同时交正文和真实调用，或返回未声明工具，明确拒绝。
3. 最终正文必须从本次临时函数的完整JSON参数还原。恢复后剥离该调用与其原生工具历史副本，把正文交给宿主显示；主聊天只有完成还原与完整性检查才能自动归档。未使用正文函数、坏JSON、空正文、缺结束、长度截断、过滤等均失败，不自动改用普通正文。
4. 上游仍使用用户选择的流式或非流式。本模式的流式响应先有界完整收取，再分流到真实工具检查或正文恢复，期间可取消；不会逐字即时显示。每个被捕获请求只发送一次，不重试、不续写，不新增输出token上限。真实工具循环有几轮，仍由宿主按实际请求计数。
5. 支持OpenAI Chat Completions及自定义Gemini generateContent。Gemini复用已审阅宿主的标准函数→原生function_declarations、required→ANY转换，保留历史；没有改为OpenAI接口请求Gemini。现有原生流的完整args和正文partialArgs由原解码器处理。
6. **当前不支持同次启用内置联网搜索或请求返回图片**，需要用户关闭对应开关；输入图片/音频/视频仍原样保留。通过标准函数工具实现的搜索可走真实工具回合。附加请求参数里的工具定义、旧functions方言、结构化输出、多候选、其他接口等明确报冲突；不通过删除用户工具、历史、搜索或图片设置强开。保留这些需求时可显式改选兼容检查模式。

本地测试覆盖两种协议、流式/非流式、真实查询与最终正文的顺序、原生签名/ID保留、配置持久保存与生产host归档门槛，以及混合/未知工具、坏参数、取消及截断拒绝。测试均为良性合成响应，没有真实模型HTTP、Rust执行或Android实机验证；alpha31.9的406字节原响应仍缺失，AT08现场根因不因本项完成而宣称已确认。
