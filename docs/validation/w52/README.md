# W52：回复失败后的 RP 恢复

## 已确认问题

W51 的生产宿主夹具可确定复现三条失败链：正文回复不符合协议、辅助回复不是合法简表、正文请求装配失败。它们会在已有准备记录后抛错，但没有完成这些准备记录的同步；随后全局基点、配置与下一轮 RP 都被 `WORKSPACE_SYNC_REQUIRED` 阻止。用户截图只给出了后续阻塞，不能据此认定手机最初触发的错误就是其中一种。

报错卡片中的“重试读取书籍与身份”没有同步；“重新读取配置状态”甚至只重新展示旧状态。真正的恢复操作位于卡片外，用户可能持续点击无效重试。

## 修改

- 对尚未写入正文、当前来源守卫仍成立的请求装配或回复校验失败，保留失败准备记录并完成物理同步。原错误继续报告，不把坏回复当正文，不自动重试模型。
- 来源、所有者或配置变化，停止，冲突，以及物理保存结果未知，继续保留待恢复记录。来源检查失败具有明确的禁止自动同步标记，优先于其他分类。
- 未被接受的正文保存在私有请求诊断中，常规错误序列化和后续模型上下文不包含它。冷重开能展示已确认的校验失败；缺乏结算证据的旧请求仍保留未知状态。
- 报错卡片提供“同步并恢复当前会话”；配置卡片提供对应恢复操作。普通配置重读实际重新载入，保留未保存草稿及首个错误，不自动初始化或覆盖已有配置。

## 验证

独立生产管线夹具覆盖：坏正文后原文保留，新显式发送成功，连续三轮与次轮归档，普通/高级重骰，销毁重建宿主后从物理书籍读回，再次发送。测试没有清除待同步记录或业务数据；只在确认无待同步后清空可重建工作缓存，以强制验证物理读回。

全量回归 2285/2285 通过（1499 根测试 + 786 V3），全部生成模块一致性检查通过。首次执行发现构建产物尚未跟上并行修改，保留原错后统一重建；首次合并执行的 V3 日志未含完整结束回执，因此另行完整执行 V3，明确取得 786 项通过、无跳过及退出码 0。未把不完整日志当全量成功。

真实 Linux TT：W51 留下的待同步记录经冷启动进入 W52，实际点击卡片恢复后完成一次物理写入、配置和绑定重载，原 9 条聊天逐字不变且无模型请求。实际发送连续三轮、正文格式错误和空响应后明确新发送均成功；每轮只发一条本地 HTTP 正文请求，无辅助调用、无待同步残留，后轮请求包含前轮正文。完整退出后冷重开，19 条消息及候选/选中候选与关闭前完全一致，全局基点和当前存档 SHA-256 均不变；辅助关闭设置保留，启动无物理写入、无模型请求、无待同步锁。

真实 TT 使用本地确定性 HTTP 响应；这不等于外部供应商或 Android 实测。手机 API 的过滤与连接超时原因仍需对应服务的实际证据，不能从本地成功外推。
