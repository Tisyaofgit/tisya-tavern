# W33 元数据回读修复

已确认的代码缺陷：`v3/host.mjs` 的 `persist()` 和楼层身份适配器将
`JSON.stringify` 的结果作为读回一致性判断。对象只有键顺序变化时也会被判错。
仅对原生回读对象递归排序、不更改字段和值，即可在打开工作台时复现用户截图的
`V3_METADATA_READBACK / 聊天元数据回读不一致：tisya_w24`。

实际上传 APK 的 `tauri/main/api/chat.js` 已确认 `metadata.get()` 调用原生命令，
不是直接返回 `getContext().chatMetadata`。现存宿主 Rust 源码通过
`serde_json::Value` 返回文件头元数据；所核 Cargo 锁依赖没有启用 `indexmap`。
相关源码散列、片段和来源分界见 `metadata-native-boundary.json`。

修复仅让对象键顺序不影响比较。字段集合、数组顺序、类型和值仍须一致；
缺失、额外字段、`0/false/null` 差异仍拒绝。比较不会调用 getter/toJSON，
也不把 `undefined`、稀疏数组等非 JSON 值静默删除后视为成功。
主会话及小缇记录回读共用该比较器；楼层身份变更判断也复用它，防止从原生
JSON 重开后仅因键顺序变化而重复保存。存储位置、原聊天及用户业务数据未改。

验证证据：

- `metadata-before.tap`：修前 7 项，2 失败、5 通过；保留相同错误与栈。
- `metadata-final.tap`：最终专项 10/10，通过冷启动、已有身份打开、排序后重开、
  原文不入库、无模型调用及缺字段/类型/数组顺序/额外字段等负例。
- `metadata-host-regression.tap`：元数据、宿主安装、被动打开、小缇相关 50/50，
  零跳过/取消。最后的无变化判定小修另由 `metadata-final.tap` 覆盖；正式全量
  验证由主任务重建最终运行文件后完成。
- `metadata-send-final.tap`：收到“正常发送也被阻断”的补充后新增发送全链与损坏
  负例，当前专项 12/12、退出码 0。每次 `metadata.get` 递归排序时，实际提取的
  manifest 拦截器完整执行一次 A 和一次 B 确定性响应、一次原生 `saveReply`、
  聊天保存、身份与来源元数据回读、原文归档及 delivered 回执；旧消息正文保持。
  将回读的 `chatId` 真正改成其他值后，仍以同一错误阻断，A/B 请求和 `saveReply`
  均为 0，现有聊天正文与内存身份保持。这里的拦截器返回 true 表示由插件接管并
  阻止重复原生生成；成功必须同时具备 delivered 回执，不能仅凭 true 判定。

边界：复现同错误不等于已取得手机原始元数据。排序误判是已经证实的代码缺陷；
用户设备是否还存在丢字段、实际值不一致或其他故障仍未知。本轮没有运行 Android
真机、APK 原生二进制或外部模型，也未操作用户真实聊天/世界书。不得将本地专项
通过写成用户设备已修复。
