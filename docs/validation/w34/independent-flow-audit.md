# W34 三步工作流独立核验

基线：本地 `5c3414ff5b0d5bf195ff5a854113f09922214812`，对应已发布 `0.3.4-w33.1`。本核验只新增测试与证据，产品变更由各实现者负责。

## 原有缺口与验证范围修正

- W33 `v3/workbench.mjs` 的初始化和历史补录都只有手工原文输入；初始化 `drawDesign` 明示“粘贴角色卡或世界资料”，历史服务 `generate` 强制要求 `source`。不存在开局建立路由。
- 老表单 `tables/service.js` 的 `cardTemplate` 及 `tables/panel.js` 曾自动取得角色卡、关联世界书、用户及历史，并提供扫描与按楼层归档；这些能力不能由 V3 的“手工资料提炼成功”代替。
- W33 集成测试 `w33-navigation-preferences.integration.mjs` 明确主动填写“待整理的资料”和“完整历史原文”，测试的是手工路径。1877 项检查通过不证明自动读取及三步工作流可用。
- 现行职责按用户确认的分工验证：初始化读取卡和配套书固定底档；开局建立再读当前用户与已选开局，并取回同一确认来源中的初值；历史按原楼层推进。原卡停用条目、示例、未选开场、后续事件不得倒填成初始化。

## 独立行为验证

测试 `tests/v3/ui-tests/w34-initialization-opening-history.integration.mjs`，5/5 通过，命令与文件 SHA 见 `independent-flow-verification.json`。

1. 从真实应用组合根挂载工作台，点击自动读取，无须粘贴。角色描述、内嵌条目和关联世界书进入实际配套提示词资料槽；原文 `{{user}}` 保持不变。初始化排除用户人设、聊天开场、备选开场、停用条目及后续剧情，生成阶段不写存档。
2. 确认固定底档后点击“继续建立开局”。配套世界书独有的精力初值 6 在初始化阶段仅提示，开局任务重新取得同一来源并保存为状态。实际已选开场和原生用户进入请求，用户档案勾选受到保护，场景引用其真实新 ID。
3. 点击“继续历史补录”，自动读当前聊天第 2—5 楼；两条 AI 回复按原序各请求一次，并分别携带此前用户楼层。摘要、变量区不作为事件证据；第一条使开局状态 6→5，第二条看见已审阅的 5，无须编造历史钟点。草案阶段不存原文；确认后两事件各有可读的真实原文引用。
4. 销毁并重建应用后，全部记录逐值一致；再次正常发送执行实际宿主拦截器 A+B，A 得到原生用户映射、两个对象、用户、两事件及当前状态，B 得到已确认事件。补录楼层不再重复进入 `archiveSources`。所有旧消息正文和原始配套世界书保持原值。
5. 负例覆盖：无确认模板时开局在模型请求前停止；关联世界书在生成后变化时保存拒绝；原生保存失败显示错误并重试同一草案，模型仍仅调用一次；历史楼层生成后被改动时，在新增原文或档案之前拒绝保存。

## 证据边界

应用、业务服务、资料槽编译、世界书前端保存代码及宿主 `saveReply` 来自真实源码；模型回答、原生字节存储和 UI DOM 是显式测试夹具。本核验不冒充真实模型、Android/WebView 或实际用户存档验收，也不证明此前手机的模块加载错误已经解决。

早期测试运行首先暴露了新测试夹具缺少角色世界书回调，随后跟随实现中的开局输入字段与组合根接线变更调整观察点；未删除来源内容、时序、读回、原文不变或失败路径断言来取得最终通过。最终证据采用实际实现已接线后的 5 项结果。
