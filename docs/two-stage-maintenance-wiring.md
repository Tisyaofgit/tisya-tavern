# 两阶段维护接线方案（待实现）

本文件是接线设计，不是功能完成声明。当前 `tables/service.js` 的 `prepare()` 仍依次执行 `archiveLoaded()`、`progressLoaded()`、`assemble()`；其中归档可能逐楼调用，`assemble()` 可能再调用偏好分析与剧情计划。本次仅迁移提示和模型业务格式，不新增一个未接线的 maintenance 模块。

## 两个实际请求的职责

| 阶段 | 输入与职责 | 不允许产生的结果 |
| --- | --- | --- |
| A：联合维护 | 当前分支的已确认未归档楼层、此前连续用户输入、经权限筛选的本地检索结果、表结构及版本、已过去的世界时间窗；先整理归档，再依据虚拟更新后的状态推演已经过去的场外变化 | 未确认尾楼入档；把未来剧情方案写成历史；代行玩家；写入长期偏好；重复运行已持久化的原生判定 |
| B：正文 | A 已确认的最终快照与检索资料、当前角色行动输入、临时场外要求、已确认且匹配作用域的用户偏好、写作要求；生成正文及展示记录 | 调用 A 的写入工具；把尚未交付的正文提前入档；将临时要求自动改为长期偏好 |

本地检索是读取步骤，不占一个模型阶段。仅需检索而无归档、无已过去世界推进工作时，跳过 A。跳过必须在状态中说明“无维护任务”，不能生成虚假的模型回执。B 应使用原生主发送通道；不能通过 `request('main')` 绕过主通道。

## 最小函数边界

1. `planMaintenance(c, loaded, type)`：只读生成计划。按当前 selected candidate chain 查来源，assistant 只有存在 index 更大的 user 时才自动视为已确认；排除 `view.archived` 中已完成来源。手动“包括最新回复”留在既有显式人工入口，不能传进自动计划。`swipe`、`continue` 必须使用现有 `load(c,type)` 的来源链，不自行拼楼层号。
2. `readMaintenanceContext(c, loaded, plan, signal)`：抽取 `assemble()` 中 personaProjection、偏好作用域过滤和本地 retrieval。工具只暴露当前 scope 的已授权条目。检索结果注明版本与来源，不是新的事实来源，不在这里调用偏好分析 API。
3. `requestMaintenance(plan, context)`：一个独立 A 请求。返回按 source key 排序的归档提案列表、一个过去世界推进分区、未解决项。禁止混入正文及永久偏好变更。格式使用统一 simple-sheet；schema 仍按现有业务定义验证。
4. `validateMaintenance(loaded, plan, response)`：在内存虚拟视图中按来源顺序调用既有 `prepareCommit`，将前一来源的提案结果提供给后一来源校验，保留来源权限、证据和 expected rev。然后从虚拟归档结果重新调用 `progressionWindow()`，核对响应的 from/to，再调用 `validateWorldProposal()`。不能预先沿用归档前的窗口，否则本次归档推进的时间会丢失。该函数不写世界书、不执行 MVU。
5. `commitMaintenance(c, loaded, validated, signal)`：继续复用唯一 `commit()`/`books.write()` 及 native settlement，不另造一套存档。返回带真实提交回执的新 loaded，只有这个新视图能进入 B。中间提交失败时保留实际完成记录并显式阻断 B，重试仅接续未提交来源。
6. `assembleNarrative(c, loaded, type, localContext)`：来自原 `assemble()`，移除其另发偏好分析/未来剧情计划的分支。临时偏好与下一步写作计划交由 B 内部执行；长期偏好候选仍走明确 review 流程，已确认偏好继续作用域过滤。最终资料仍经 `materialSlots()` 和字符预算，不静默裁剪必需事实。

## 原生变量与批次缓存

当前 nativeBridge 有单楼来源锁、parsedNative 缓存、持久化 nativeReceipt 和防重复随机判定逻辑。联合 A 的缓存不得替代这些回执，也不得仅凭模型声称“已执行”视为写入。建议先在非 nativeBridge 路径启用联合 A；原生路径只有完成以下门禁后才接入。

- 批次指纹包含 world key、角色卡/聊天/分支标识、origin/session identity 与修订、所选候选链（含正文和 candidate）、规则版本、玩家绑定、检索输入与所见条目版本、世界时间窗。来源编号相同而文本变化也必须失效。
- 计划、模型提案、已验证批次、持久化回执是四种状态。缓存模型提案只能减少重试调用，不代表已验证或已写入。
- 批次验证完成前不持久化。逐来源写入以后，以真实存档回执更新进度；提交失败不能重跑此前已结算的 MVU 骰点或回滚已成功的外部操作。
- 原生结算更改投影后，必须重新校验后续提案的 expected rev 和世界窗口。不能为让旧批次通过而自动改版本或重新分配临时 ID。
- 每次 await 后检查原 `c.guard()`、abort signal 和存档版本。卡、聊天、persona、分支或规则变化，丢弃未提交候选，禁止注入 B。
- 内存缓存应有限容量与有效期，完整成功或上下文切换后清理。没有持久化回执时只能说“待确认”，不能说可跨重启恢复。

## 接通前必需验证

1. 无工作：A 零调用，B 一次正常主发送；本地检索仍有效。
2. 两个已确认楼层加一个候选尾楼：只提交前两楼，各自证据和来源独立；重试无重复归档。
3. 归档使世界时间前进：A 先虚拟归档再生成正确过去窗口；拒绝未来、玩家行为、未知秘密和过期依据。
4. A 失败或格式错误：不注入部分维护结果到 B；若已产生持久化外部效果，明确展示实际进度，不伪称整体回滚。
5. 切卡、切聊天、切 persona、重骰、分支切换、修改原文、改规则以及取消：缓存均不能跨 scope 复用。
6. 原生变量：同一来源随机判定只执行一次，原生回执丢失时阻断重放；表格和前端读同一已结算快照。
7. 临时偏好只进入 B，本轮重骰按既有绑定沿用；长期偏好未经确认不写入，不进入不匹配的人物/世界。

未完成这些真实接线和测试前，交付应写“当前请求仍按原服务任务分别调用；两阶段联合调度待实现”。
