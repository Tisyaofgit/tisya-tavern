# W9 对象档案与用户偏好消费者审计

- 审计基线：`settings-ui-work`，HEAD `e598a0a`。
- 审计时间：2026-10-23 04:20—04:32 UTC。
- 范围：只读源码审计及中性 Node 内存 fixture；未修改产品、未调用真实模型、未改用户世界书或存档。
- 结论：极简填表线协议已接入辅助任务入口；对象档案的单次行落位已经存在。动态用户偏好尚未迁移为七分类＋场合触发。当前“完整参考档案”可制作，但必须区分可直接消费的现有字段、展示整理层和待实现的新分类路由，不能把新外观当作已接线的数据格式。

## 1. 必须先保留的真实边界

1. `service.js:49–54` 的真实模型文本只进入 `parseSimpleSheet`（规则校对专用 parser 除外）；不会回退到旧 JSON 文本解析器。内部 executor 可以传已经类型化的对象。`ledger.js` 中仍保留旧 `parseJSONResponse` 导出，但本次读取的 service 模型入口没有调用它。内部对象/持久存储使用 JS 对象不等于对模型要求复杂 JSON。
2. 读档先经过 `project` 选择实际保留分支的 source/depends/contextSource；之后身份、偏好范围、条件、引用闭包、自然语言投射依次执行。模型只能看到这个节点的记录，不能将记录的 `updatedAt` 宿主时间当故事时间。
3. `prepareCommit` 核验连续原文 evidence、expected rev、来源时序、允许的业务表、引用和当前行唯一性；未知/缺失不能凭格式补全。当前状态以 `(对象, 字段)` 唯一；场景全局唯一；人物成长以 `(主体, 方面)` 唯一。归档的历史证据不自动获得修改后续当前值的权利。
4. 当前用户对象的基础说明由原生 persona 唯一持有；`personaProjection` 会以原生当前定义替代绑定对象的基础投射，原始表内其他属性不会自动一并展示。参考稿须明确区分“本节点绑定的角色”与现实用户偏好，不能让偏好数据成为人物知识。

## 2. 默认真实表和字段

所有行都有 `id/table/rev/values/access/source` 等外壳；所有表 `名称` 必填。以下是默认业务表字段，不应假称只有“人物、快照、历史”三个存储表。

| 表 | 字段与关键约束 |
|---|---|
| objects | 类型必填；别名、世界、描述、核心引用、关联、标签、发现环境、属性。发现环境包含地点、时段、出现条件、来源依据、确认程度、可复用。 |

| state | 对象、字段必填；有效性=有效/失效/待确认；值、值引用、原生引用三选一；生效时间、失效时间、变动原因。 |
| relations | 主体、对象必填；维度、好感、声望、印象、锚点事件、证据、生效时间。好感/声望分正面与负面；刻度保留值、最小/最大、端点、依据和原生引用。 |

| timers | 时间基准、起点、到期时间、触发条件、失效条件、重复规则、到期轮次、任务；状态=等待/到期/完成/取消。 |
| clues | 已出现内容、阶段、公开范围、推进条件、事件、对象。 |
| events | 时间、时间范围、地点、经过、结果、场面、台词、意象、前因、影响、后续、情感余波、触发线索、参与者、关联/前置/后续事件、标签、原文段落。 |
| activities | 主体必填；目标、行动、开始时间、推进至、预计结束、阻力、下一步；进度 0–100；状态=计划/进行/等待/完成/取消；任务、地点、知情依据、锚点事件、资源。 |

| growth | 主体必填；方面、原有倾向、当前倾向、变化依据、反例、生效时间、锚点事件；阶段=萌芽/积累/稳定/回退；原生引用。 |

默认对象类型只有五个，且可用有依据的兼容扩展新增类型/可选字段：

- character 人物：身份、外貌、性格、背景。
- item 物品：形态、用途、材质、规则。
- place 地点：环境、位置、特征、出入条件。
- rule 规则：适用范围、条件、效果、例外。
- organization 组织：职责、结构、立场、历史。

字段语义建议：身高/年龄等如果没有来源就省略或在阅读稿明确“未给出”，不要填写 0、空文本或猜测值；并非每种人物字段都必须为了“全档案”伪造实例。全覆盖应指实际存在的全部对象和偏好、以及完整说明可用字段，不应指杜撰所有类型的对象。

## 3. 对象档案、快照、待办：已做与剩余缺口

`story-material.js:64–115` 的 `projectStoryDossiers` 是无写入的投射器：重复稳定 row ID 直接报错；每个被选中的 row 只有一个 placement。对象自身和所属 facts 进入 Basics；state/relations/cognition/activities/experiences/growth/holdings/clues/tasks 根据明确所有者进入 ToNarrate。事件集中在 History；preferences/native_cells 分发外部目的地。多所有者、所有者未选中或只有薄身份的行不会猜归属，而进入全局材料。

需要明确的限制：

1. **“单次行落位”已做到，“同一事实语义全链唯一”尚未完成。** `service.js:439–443` 在 dossier 后仍拼接 `storyContext`；原生当前值在 `<当前已确认状态>`，已确认的状态/条件结算在 `<已确认变化>`，没有统合成对象的 Basics/ToNarrate。文本若原本已经重复写在多个源行，projector 也不会自动判定并删除。
2. **ToNarrate 目前不是严格的“仍待完成事项”。** 五种 task 状态全部会进入 ToNarrate 或 NarrativeAgenda，完成/取消状态虽完整保留，但所在标题容易被理解为仍待执行。参考稿应标明“已接受未完成”“待答但未接受”“他人意图”“已结束”四种语义，结束的任务不要列为用户义务。
3. `CAPTURE_RULES.pending` 已要求“已接受约定、已启动事务或真实待答问题；拒绝、意图或到期不等于完成”；偏好及剧情指南也明确 NPC 主动不等于玩家同意。但 schema/commit 没有“接受依据”状态转移守卫，中性 fixture 证明一条 `状态=发布、负责人=[玩家]` 的 NPC 愿望仍可合法写入。因此不能仅因负责人字段就宣称玩家已经接受。
4. `state.有效性` 可省略。condition 默认排除“失效”，保留“待确认”；最后已知值不等于当前确证。阅读稿应在每个待确认状态旁保留有效性/来源时点，不能将旧地点直接写成当前所在地。
5. 原生快照从指定 messageIndex 向前找，不读未来；缺路径列 missing，无接口/无旧快照明确 unavailable。到期检查只使用绝对保留 AI 楼层数或唯一当前场景的可比较公历时间，`明日/三天后` 未解析时 due=null，不借宿主日历推断。due=true 只是触发检查，不是任务完成。
6. 每行保留 readers 与 knowers；读者可见不授予人物知情。引用闭包也不复制父行权限。模型资料中的权限是叙事约束，不能把它描述为逐行网络访问控制。人物心理、误信、推测都须在 cognition 的主体/确认程度里区分。

## 4. 用户偏好：真实可消费状态

### 4.1 两条路径尚未合一

- **固定配置**：`config/english-preset.js:16–34` 编译七组 GlobalWritingRequirements / NarrativeComposition / ProhibitedWordsAndPatterns / CharacterPortrayal / PlotPreferences / SpeechHabits / DictionAndStyle。已包含语言、双语对白、篇幅、叙事模块、主动性、用户口癖与 user 叙事口吻、心声、文风资源等配置。自定义空文本是用户清空，不能被默认规则补回。
- **动态已确认偏好行**：`schema.js:33` 仍是旧六枚举：用词、NSFW题材、SFW角色表现、剧情走向、文风、特定情节。`storyPreferences` 将有效已确认行逐条自然语言输出，没有七组归类，也没有基建/战斗/恋爱等场合开关。

七组参考稿可按用户要求整理，但必须保留其旧存储类别映射，标注场合规则属于本次设计/阅读标注。不可承诺七个中文新枚举能直接覆盖现有 类别 字段。

### 4.2 真实字段语义

- 性质：明确要求 / 推测偏好。
- 强度：必须 / 喜爱 / 厌恶 / 禁止 / 偏好；程序禁止“推测偏好+必须”。
- 作用域：全局（存储归属），以及用户角色、角色卡、世界、会话四个准确 ID 列表。非空维度之间 AND，同一维度列表项 OR。空列表不施加限制；缺失 scope 在 matcher 中匹配全部当前上下文，不代表当前记录会自动跨存档传播。
- 用户角色可匹配原生 persona ID；传入有效 binding 时也可匹配绑定对象 ID。
- 倾向区间：每轴有左端、右端、下限、上限、依据、说明；端点范围 -100..100，下限≤上限，端点必须不同。不是单一线性用户人格评分。
- 置信度目前仅 number，没有默认 0..1/0..100 限制。参考稿如用百分比必须注明单位，不要声称程序有这个量纲。
- 例外、范围、内容可以存文字，但 scope matcher 不把这些自由文本转成可执行场合条件。

### 4.3 已确认的消费者缺口

1. 默认 schema 拒绝未登记 `场合` 和七组新 类别 值。更隐蔽的是本地 `prepareCommit` 默认可推断新增可选字段，所以本会话可能成功存进 `场合=[战斗]`，然而 `preferenceMatches` 完全不检查它；全局保存又按 defaultRegistry 校验并拒绝新字段/模板变化。因此会形成“局部可存但条件不执行、全局不可保存”的不一致。不能用自由字段先假接线。
2. `assemble` 给 preferenceMatches 传 persona binding，而 `invoke → activePreferences` 没传 binding。仅以绑定对象 ID 为用户角色 scope 的偏好，正文投射可匹配，辅助任务调用会排除。需在迁移时统一消费者输入。
3. `storyPreferences` 的 scope 是 texts，直接显示 host persona/chat/card ID；不是 schema 的 ref，不能走人名映射。作为给模型的内部上下文尚可，但不适合“隐藏背后逻辑”的用户阅读版全档案。
4. `assemble` 会在 preferences 开启时为当前 user 调用一次独立 preferenceAnalysis；plot 开启又独立调用 plotAdvance。该实现仍不是用户提议的默认两次请求合并流程。不得把即将开展的格式接入当作调用数优化完成。

### 4.4 确认、保存、回读、再注入

`analysePreferenceSource` → invoke/parse → prepareCommit 预检 → 写入 pending 草案（尚未影响正文）→ `reviewPreference` 校验来源仍活跃 → `commit` 标记 preferenceConfirmed → 本地 session commit 或全局 bank 保存 → load/project 合并已确认全局行 → scope/启用/confirmed 过滤 → storyPreferences。

草案状态 pending/empty/accepted/rejected，确认状态不写成用户偏好内容。重骰反馈需真实方向文字和 remember；仅“重新生成”不证明喜好。全局保存和本地保存分批，禁止一次混写；全局行 source=null、knowers=[]，确认凭据绑定 draft ID 与世界。正式接入必须验证此链保存后重新 load 的结果，而不是只观察内存预览。

## 5. unknown 与空值

- typed simple sheet round trip 已验证 null、0、false、空文本、空列表、空对象互不混淆；缺失可选字段省略。state 必须有值/值引用/原生引用之一，因此“未知但保留最后已知”要通过有效性表达，不能把 undefined 持久化成值。
- dossier 投射 `preserveEmptyTypes:true` 已验证：null→明确空值，0→0，false→否，空文本→空文本，[]→空列表，{}→空对象。
- **仍有缺口**：storyContext 的原生快照及 before/after 变化使用 storyValue 默认值，null→未设定、空文本→空白、[]/{}→无。这条旁路没有达到 dossier 的空值区分能力。
- patch 的语义独立于 wire 类型：自动 merge 对 object/map 做增量合并，提交 `{}` 通常不清空旧对象；要清除可选字段走 unset，人工替换才用 replace 语义。不要告诉用户“填空对象必然清空已有字段”。

## 6. 推荐首个最小接入切片

建议本轮只验收一个真实闭环：**从一个已确认节点的简表增量，经过现有解析/校验与草案预览，保存并重新载入，再投射为同一对象的 Basics/ToNarrate；preferences 同批产出仍作为待确认候选，不顺手永久生效。**

1. 用真实最新节点冻结 source key、分支、故事时间，建立全对象索引；不补造缺席人物、不把早期口吻视为现有偏好。
2. 一个批次覆盖稳定身份、当前状态、历史事件、已接受待办/未接受提议各一项；用 stable ID 引用，不重复整份档案。兼容扩展必须明确映射，不无声推断场合执行语义。
3. 暂保留旧 preferences schema 的确认/保存机制；用户阅读参考按七类排版，按“全局/当前卡/当前会话/场合候选”标出适用范围。明确暂未支持的场合只读，不虚构已生效开关。
4. 可同步做的很小呈现修正：storyContext 调用 storyValue 时启用空值区分；为 task 发布/结束状态加明晰语义，避免把 NPC 希望列成玩家义务。这不应改写原事实或自动变更任务状态。
5. 后续真正迁移场合时，一次贯通版本化 schema、局部/全局迁移、确认编辑、条件引擎、正文与辅助任务共同 matcher、七组投射和重载测试。不要只新增一个“场合”文本栏。保留用户明确指令优先、禁用/例外、未知场合不猜、冲突可追溯。
